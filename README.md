# frame_channel

C++20-модуль для передачи кадров от producer к consumer с ограниченной памятью
и приоритетом свежести: при переполнении выбрасывается самый старый кадр из
очереди, producer никогда не ждёт consumer.

- `include/frame_channel/frame_channel.hpp`, `src/frame_channel.cpp` — модуль;
- `examples/basic_usage.cpp` — пример (медленный consumer, остановка, перезапуск, ошибка);
- `tests/frame_channel_test.cpp` — тесты без внешних зависимостей;
- `bench/frame_channel_bench.cpp` — benchmark задержки и аллокаций.

## Сборка и запуск

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
./build/basic_usage
./build/frame_channel_bench

# санитайзеры
cmake -S . -B build-tsan -DFRAMECHAN_SANITIZE=thread && cmake --build build-tsan -j
cmake -S . -B build-asan -DFRAMECHAN_SANITIZE=address,undefined && cmake --build build-asan -j
```

Нужен компилятор с C++20 и CMake ≥ 3.16. Проверялось на GCC 13.3, Linux x86-64.

## Модель

Вся память выделяется один раз в конструкторе:
`queue_capacity + max_read_leases + max_write_leases` буферов по
`frame_capacity` байт (с выравниванием 64). Каждый буфер находится ровно в
одном состоянии:

```
Free -> Writing (WriteLease) -> Queued -> Reading (ReadLease) -> Free
```

- Вытесняются только буферы в состоянии `Queued`. Буфер под `ReadLease` или
  `WriteLease` никому не выдаётся, пока lease не уничтожен.
- Из размера пула следует: пока producer соблюдает лимит `max_write_leases`,
  `acquire()` всегда находит свободный буфер — producer не блокируется и не
  получает отказ, как бы долго consumer ни держал кадр.
- Consumer, превысивший `max_read_leases`, получает `Status::LeaseLimit`, а не
  чужой буфер.
- Lease держит `shared_ptr` на память канала, поэтому может пережить объект
  `FrameChannel`.

```cpp
framechan::FrameChannel channel({.frame_capacity = 640 * 480, .queue_capacity = 2});

// producer
auto [st, lease] = channel.acquire();
fill(lease.buffer());                           // запись прямо в буфер канала
channel.publish(std::move(lease), frame_size);  // при переполнении вытеснит старейший

// consumer
auto [st2, frame] = channel.receive(framechan::Take::Newest);
process(frame.data(), frame.info());            // буфер неизменен, пока жив frame
```

### Остановка, перезапуск, ошибки

| Вызов | Эффект |
|---|---|
| `stop(Drain)` | новые кадры отклоняются (`Stopped`), consumer дочитывает очередь, затем получает `Stopped` |
| `stop(Discard)` | то же, но очередь сбрасывается сразу |
| `fail(ec)` | как `stop(Discard)`, consumer получает `Failed`, `error()` возвращает `ec`; первая ошибка побеждает |
| `restart()` | `Stopped/Draining/Failed -> Running`, очередь и ошибка сбрасываются |

`stop`/`fail` идемпотентны, вызываются из любого потока и будят всех ждущих
consumer. Тонкие места:

- consumer, ждавший в `receive()` во время `stop()` + `restart()`, вернёт
  `Stopped`, а не продолжит ждать уже в новом сеансе (проверяется номер эпохи);
- `WriteLease`, полученный до `restart()`, при `publish()` даёт `Stale` — кадр
  прошлого сеанса не попадёт в новый;
- `ReadLease`, удерживаемый через `stop()`/`restart()`, остаётся валидным и
  продолжает занимать слот лимита;
- `publish()` с неверным размером или чужим lease возвращает `InvalidArgument`
  и не трогает lease; в остальных случаях lease поглощается;
- конструктор бросает `std::invalid_argument`, `std::length_error`,
  `std::bad_alloc`; остальные методы `noexcept`.

`FrameInfo::sequence` монотонен на всё время жизни канала, пропуски означают
потерянные кадры. `stats()` даёт счётчики с инвариантом
`published == delivered + dropped_* + queued`.

## Тесты

16 тестов, в том числе: медленный consumer (20 000 кадров, содержимое
удерживаемого кадра проверяется после паузы), переполнение, удержание кадров
при 1000 публикаций поверх, 300 итераций конкурентного `stop()` из 4 потоков
при работающих producer и consumer, 500 циклов `stop/fail` + `restart` под
нагрузкой, MPMC. Проходят в Release, под ThreadSanitizer и под
AddressSanitizer + UBSan.

Тест «`stop()+restart()` будит ждущего» не может снаружи узнать, что consumer
уже заснул, поэтому допускает до 10 % опоздавших итераций.

## Benchmark

`frame_channel_bench [--frames N] [--bytes N] [--period-us N] [--slow-work-us N] [--runs N]`

Producer публикует кадр каждые `period-us`, consumer берёт самый свежий.
Сравнение — с намеренно простой очередью с той же политикой, но с
`std::vector` на кадр. Аллокации считаются подменой `operator new` только в
установившемся режиме. Код возврата ненулевой, если `FrameChannel` выделил
память хотя бы раз.

Замер: 2 vCPU, общая виртуальная машина, GCC 13.3 `-O3`, параметры по умолчанию
(2000 кадров × 5 прогонов, 921 600 байт, период 1 мс, медленный consumer 3,5 мс
на кадр). Время в микросекундах.

| Сценарий | Реализация | задержка p50 | p90 | p99 | producer p50 | producer p99 | аллокаций/кадр | потери |
|---|---|---|---|---|---|---|---|---|
| быстрый consumer | FrameChannel | 24,4 | 37,1 | 45,4 | 30,9 | 101,2 | 0 | 1,5 % |
| быстрый consumer | vector queue | 24,2 | 37,1 | 55,1 | 40,1 | 122,0 | 1,06 (≈0,9 МБ) | 1,6 % |
| медленный consumer | FrameChannel | 544,9 | 994,8 | 1101,1 | 13,1 | 93,0 | 0 | 71,4 % |
| медленный consumer | vector queue | 543,7 | 991,4 | 1104,9 | 22,4 | 91,7 | 1,06 (≈0,9 МБ) | 71,4 % |

Что из этого следует и что нет:

- Аллокаций в установившемся режиме нет — это проверяется при каждом запуске.
- Стоимость кадра на стороне producer по медиане ниже примерно на 10 мкс
  (второй прогон дал те же ≈10 мкс).
- **Задержка передачи от простой очереди не отличается**: она определяется
  пробуждением потока через `condition_variable`, а не каналом. Возраст кадра у
  медленного consumer задаётся политикой «брать свежий», одинаковой у обоих.
- Максимумы (в таблицу не включены) на общей машине шумные: от 0,3 до 23 мс
  между прогонами. Хвосты нужно мерить на целевом железе, с привязкой потоков
  к ядрам. Потери 1,5–4 % в «быстром» сценарии — следствие того же шума.
- Не измерялось: MPMC под нагрузкой, другие размеры кадра, другие ОС и
  компиляторы.

## Компромиссы

- **Один mutex на все операции.** Критические секции — десятки наносекунд
  (перестановка индексов), но producer может быть вытеснен, держа блокировку,
  и возможна инверсия приоритетов. Для hard real-time producer лучше подойдёт
  lock-free «тройной буфер» (SPSC, три буфера, обмен одним атомарным индексом):
  он wait-free, но даёт только «последний кадр», одного producer и одного
  consumer, без очереди и без нескольких удерживаемых кадров.
- **Пробуждение через `condition_variable`.** Это и есть измеренные ~25 мкс.
  Если нужна задержка в единицы микросекунд и есть свободное ядро — активный
  опрос `try_receive()`; ценой 100 % загрузки ядра.
- **Память фиксирована и рассчитана на худший случай**: `(Q + R + W)` буферов
  максимального размера. При сильно разных размерах кадров (сжатое видео) или
  редких кадрах экономнее пул с классами размеров или обычные аллокации —
  по замеру выше они стоят около 10 мкс на кадр в 0,9 МБ.
- **Потери — часть контракта.** Если терять кадры нельзя (запись на диск,
  кодирование с межкадровой зависимостью), нужна очередь с блокировкой
  producer (backpressure), а не этот модуль.
- **Один получатель на кадр.** Для рассылки одного кадра нескольким consumer
  нужен подсчёт ссылок на буфер; здесь этого нет.
- **Lease держит `shared_ptr`**: два атомарных инкремента/декремента на кадр в
  обмен на безопасность при уничтожении канала раньше lease.
- **Буфер не обнуляется.** `WriteLease::buffer()` содержит данные предыдущих
  кадров; consumer видит только первые `size` байт, которые producer обязан
  заполнить.
- **Только в пределах процесса.** Для межпроцессной передачи нужна разделяемая
  память и другой механизм владения.
- `prefault = true` трогает все страницы в конструкторе: дольше старт, зато
  первые кадры не платят за page fault. Память не закрепляется (`mlock`).
